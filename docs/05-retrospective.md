# 05 复盘（最难问题、学习收获、下一步）

## 1. 最难的问题

### 1.1 「重规划」不等于「再跑一遍」

题目要求最容易被做错的地方，是把动态决策实现成「失败就从头再来」：

```
检索 → 脚本(失败) → 检索 → 脚本(失败) → ... → 超步数上限 → 未完成
```

这在功能上"能过"部分验收点，但按题目原话 ——
「高分依据是合理重规划；无状态、无失败处理只能证明完成串行调用」—— 会被判为低分：
因为它既没有状态（不知道上一步成功了什么），也没有真正的重规划（只是重复）。

真正的重规划需要三件事：

1. **知道失败在哪一步** —— 失败必须带 `failed_asset_id`（哪个素材的脚本没生成出来）。
   第一版的错误信息只说「脚本生成失败」，模型无法区分「全部素材都失败」和
   「其中一个素材失败」，于是只能整组重来。
2. **知道什么已经成功** —— 步骤状态落库（`(run_key, step_name)` 唯一），
   成功步骤的结果可以被读回复用。
3. **有可用的替代空间** —— 服务端在估算超限时给出 `alternatives`，
   模型只需**选择**，不需要自己造组合（模型造组合容易出现重复素材或超预算）。

这三件事齐备后，`tool_failure` 的 trace 才变成：

```
1 search_materials   检索成功
2 generate_script    失败（A04）
3 generate_script    重试，仍失败
4 generate_script    换素材 A06 —— decided_by=observation.error.detail.failed_asset_id
5 estimate_cost      8，在预算内
6 save_plan          保存成功
```

**检索只发生一次**，说明成功结果被保留，而不是重头再来。

### 1.2 替代方案的排序：省钱 vs 保内容

第一版的 `find_alternatives()` 按**总费用升序**排序。看起来很合理，但实际输出是：

| 方案 | 费用 | 保留的原素材价值 |
|---|---|---|
| `[A09]`（社群快讯模板） | 5 | 0 |
| `[A05]`（信息流广告素材包） | 7 | 4 |
| `[A06]`（博客长文） | 8 | **5** |

排序把 `[A09]` 排在最前 —— 最便宜，但和「品牌推广」这个主题**毫无关联**，
等于为了省钱把内容方向换了个主题。运营拿到这样的方案不会满意。

修正后的排序键：

```
retained_value 降序  →  retained 降序  →  total_cost 升序
```

即**优先保住原方案中价值最高的素材**，其次保留更多素材，最后才比价格。
结果变成 `[A06]`（8）排在 `[A09]`（5）前面 —— 省钱，但方向不跑偏。

这个问题的本质是：**「可行」不等于「合理」**。评分表里写的是「合理重规划」。

### 1.3 「超预算」不能只在提示词里约束

早期版本里，模型被提示「不要超预算」，但**没有任何代码阻止**它保存一个 12 元的方案。
提示词约束在真实模型下不可靠。

最终的做法是：让「超预算」成为**服务端算出来的事实**，
并让替代组合也由服务端给出。模型只在合法选项里挑。
这样即使模型想超预算，也没有对应的工具入参能实现（`save_plan` 前的费用校验会拦住）。

**提示词是引导，代码才是约束。** 项目里所有四条硬性约束都有对应的代码层强制。

### 1.4 状态写入会覆盖模型的决定

`_absorb()` 里原本有这一段：

```python
if action.tool == "search_materials":
    state["assets"] = [c["asset_id"] for c in cands[:2]]   # ← 覆盖
```

问题：模型在下一步 `generate_script` 的 `args` 里给出了自己选的素材，
但下一轮 `_absorb` 又用「前两个候选」把 `state["assets"]` 覆盖掉了。
结果模型的选择被丢弃，后续估算用的是系统替他选的组合。

修正：检索只更新 `state["candidates"]`（候选池），
`state["assets"]` 以模型在 `generate_script` / `estimate_cost` 的 `args` 中回传的选择为准。
一句话：**工具提供事实，模型做选择，状态不能替模型做选择。**

### 1.5 续跑时忘记继承失败计数

`fail_times=2` 的语义是「前两次失败，之后成功」。第一次执行失败 2 次后中断，
如果续跑时**不继承失败计数**，工具上下文会认为「还没失败过」，
于是又失败 2 次 —— 续跑永远完不成。

修正：失败计数写入 `run_meta` 表，续跑时 `load_failure_counts()` 恢复。
这是「状态」真正发挥作用的地方，也是「失败步骤续跑」这个加分项能成立的前提。

### 1.6 契约被一个空列表「影子覆盖」

补测试时发现：`src/agent/loop.py` 里写了

```python
from ..tools.contracts import TOOL_SPECS   # 导入
...
TOOL_SPECS: list[dict[str, Any]] = []      # 又把它清空了
```

结果**决策层拿到的工具列表始终是空的**。

为什么一直没暴露？因为离线 Mock 客户端**不读** `tool_specs` 参数 ——
它自己知道有哪些工具，于是流程照跑不误。而真实模型通道
（`openai_compat.py`）是把 `tool_specs` 序列化进 system prompt 的，
一旦切到真实模型，模型就会收到「可用工具：[]」，完全无从下手。

**教训**：Mock 实现和真实实现共用协议，但**不代表 Mock 会用到协议的每个字段**。
这类「契约形同虚设」的缺陷，只有当有一条独立的测试直接断言契约内容时才会被发现 ——
所以补了 `tests/test_contracts.py`，直接断言四个工具名与各自的 `required` 字段。

### 1.7 重试计数的 off-by-one
第一版把 `fail_times` 当作「已用次数」判断，
写成 `if used <= fail_times: 失败`，结果 `fail_times=2` 时失败了 3 次。
更隐蔽的是 `fail_times=0` 被当成「不限制」→ 变成永久失败，语义完全反了。

修正后的语义（写在 `ToolContext._injected_failure` 的注释里）：

| 配置 | 语义 |
|---|---|
| 省略 / `null` | 永久失败 |
| `0` | 永久失败 |
| `N > 0` | 前 N 次失败，之后成功 |

并补了单测 `test_generate_script_injected_transient_failure` 固化这个语义。

## 2. 学习收获

1. **确定性计算必须留在代码里。** 费用、时限、幂等这些「一算错就全盘错」的东西，
   交给模型等于放弃可回归性。本项目把模型的作用范围压缩到「选择」，风险大幅下降。
2. **失败信息的设计比失败处理更关键。** 抛一个带 `failed_asset_id` 的错误，
   比抛一个「失败了」的异常有用得多 —— 它直接决定了模型能不能重规划。
3. **观测驱动要可被证明。** `decided_by` 字段 + 断言测试，
   比在文档里写「本项目实现了 ReAct」有说服力得多。
4. **幂等要落在唯一约束上。** `plan_key = hash(topic|assets|cost)` 唯一索引，
   重复执行天然返回 `duplicate`，不依赖应用层判断。
5. **交付材料要能一键复现。** `gen_outputs` / `check_delivery` / `check_secrets`
   三个脚本让评审不需要相信文档，只需要跑命令。

## 3. 如果继续做，会怎么做

按优先级：

1. **真实模型回归**：把 8 个用例接到真实模型通道跑一遍，
   统计「超预算时改选正确率」「失败时换素材正确率」，
   用数据替代 Mock 的确定性结论。
2. **替代组合升级为最优求解**：当前是启发式（移除 / 替换 / 单素材），
   素材多时可以换成 0/1 背包或整数规划，保证「保留价值最高 + 预算内」是真最优。
3. **部分成功的更细粒度**：目前「脚本生成失败」是整体失败 + 逐素材标记；
   可以做成「同批次内部分素材成功」，只对失败素材换料。
4. **并行工具调用**：检索与素材详情可并行，缩短端到端耗时。
5. **耗时模型接入真实队列**：把固定分钟数换成实际任务队列的预计完成时间。
6. **人工确认环节**：目前方案直接落库；
   生产场景应像项目 1 一样加「待确认」态（金额较大的改单需人工确认）。
